# Architecture

Karma's World uses a modular monolith: a single web application with clear feature boundaries for learning, practice, community, and accounts. Domain data and UI are separated under `src/data` and `src/components`.

## Safety boundary

The first release contains educational content and simulated interactions only. Never run learner-supplied commands in the web server process. Any future hands-on lab runner must be a separately isolated service with short-lived, least-privilege containers, strict resource limits, network controls, and disposable filesystems.

## Planned evolution

- Phase 1: responsive academy homepage and navigation.
- Phase 2: lesson content, path navigation, quizzes, and browser-local guest progress are implemented. Signed-in learner progress syncs through the account API; guest progress remains on the current device.
- Phase 3: browser-only phishing, password habits, network defense, and mini CTF games are implemented with fictional scenarios.
- Phase 4: browser-only, fixed-example practice simulations are implemented. Real hands-on labs remain future work and must use a separately isolated service with short-lived, least-privilege containers, strict resource limits, network controls, and disposable filesystems.
- Phase 5: a learner dashboard and career roadmap are implemented. The account interface supports registration, login, logout, session restore, and progress sync.
- Phase 6: printable course completion records are available after all lessons in a path are complete. They are personal learning records, not accredited qualifications.
- Phase 7: the community includes guided conversation prompts, a private per-account reflection journal, and a moderated discussion board. New posts stay pending until an administrator approves them; learners can report approved posts, and administrators can approve, hide, and resolve reports. Public discussion is limited to this reviewed MVP and still needs operational moderation coverage before broad launch.
- Phase 8: a public opt-in leaderboard ranks participants by server-recorded lesson completions. Participation defaults to off, exposes only the account display name and completed lesson count, and can be withdrawn at any time.
- Phase 9: a dated security brief presents editor-reviewed summaries linked to official advisories and standards bodies. The headlines and dates are attributed, original pages open separately, and the brief displays its last-curated date. Editorial refresh remains a manual task; do not treat the page as a real-time alert channel.
- Phase 10: administrators have a role-protected overview of aggregate learner and moderation counts, with a shortcut to the moderation queue. It does not expose learner email addresses or individual progress records. Account role changes remain restricted to trusted database administration.
- Phase 11: administrators can draft, edit, publish, and archive security brief items. New items start as drafts; public readers receive published items only. Links are restricted to HTTPS pages on NIST, CERT-In, or CISA domains, and the brief carries an editorial verification date.
- Phase 12: learners can download a portable JSON snapshot of their progress and private reflections. Signed-in exports also include account progress, their community posts and reports, and leaderboard participation. The account export is authenticated, not cached, and excludes password hashes and session data.
- Phase 13: signed-in learners can update their display name and change their password in account settings. Password changes verify the current password, require a new password of at least 15 characters, rotate the active session and CSRF token, and delete other active sessions.
- Phase 14: new accounts must verify their email before sign-in. Learners can request a password reset by email; verification links expire after 24 hours, reset links after one hour, and each link can be used once. Only token hashes are stored, requests avoid disclosing whether an email has an account, and completing a reset removes all active sessions. Existing accounts are marked verified during migration.
- Phase 15: learners can delete their account after confirming the current password and typing `DELETE`. Deletion removes their database account, learning progress, community posts and reports, leaderboard entry, tokens, and sessions; the current browser also clears account-scoped progress and private reflections. The final administrator account cannot be deleted.
- Phase 16: learners can optionally protect sign-in with an authenticator app. Enrollment requires the current password and confirmation code; authenticator secrets are encrypted at rest, TOTP codes are replay guarded, and one-time recovery codes are stored as hashes and shown once. MFA challenges expire, and password changes, account deletion, and MFA disable also require a second factor when MFA is enabled. Enabling or disabling MFA revokes other sessions and rotates the current session. Production deployments must keep a stable private `MFA_ENCRYPTION_KEY` outside source control.
- Phase 17: account settings show active sign-ins with a browser label, sign-in time when known, expiry, and the current device marker. Learners can end one other session or all other sessions while keeping the current one. Session records stay in the PostgreSQL session store; the application stores a bounded browser label and timestamp, not an IP address.
- Phase 18: learners with MFA enabled can replace their recovery codes after confirming the current password and an authenticator or unused recovery code. Rotation consumes a recovery factor if used, invalidates the complete previous set, returns ten fresh codes once, and rotates the active session while ending other sessions.
- Phase 19: learners can request an email change after re-entering their password and, when enabled, MFA. The current address remains active until a single-use link sent to the new address is explicitly confirmed. Confirmation updates the verified address, notifies the old address, invalidates other account tokens, and ends all sessions.
- Phase 20: account settings show a private security activity history for successful sign-ins and important account-security changes. The API returns only the signed-in learner’s latest 50 events, keeps a bounded browser label, stores no IP address, and includes this history in the learner’s account export.
- Phase 21: a searchable cybersecurity glossary explains 23 core terms in plain language, groups them by topic, adds practical examples, and opens the related lesson directly in the learning academy.

## API foundation

The API package provides email-verified registration, login, optional authenticator MFA, logout, session inspection, private security activity history, account profile updates, password changes and recovery, self-service account deletion, and authenticated learning-progress endpoints. It uses PostgreSQL-backed sessions and Prisma models for learners and lesson completion. The frontend synchronizes on sign-in and when a lesson is completed. Local storage keeps guest progress separate from per-account caches. The site remains usable without the API, but account features require the API, PostgreSQL, and an SMTP service to be running. Public release still needs operational email delivery, account recovery support, and deployment hardening.
