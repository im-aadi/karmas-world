# API foundation

The API is a separate module inside the modular monolith. It uses PostgreSQL through Prisma, server-side sessions, Argon2id password hashes, request validation, login throttling, exact development CORS origins, CSRF tokens for state-changing routes, and HTTP-only SameSite cookies. Production sessions use a `__Host-` cookie with the Secure attribute.

## Local setup

1. Install Docker Desktop and start it.
2. From the project root, run `docker compose up -d database mailpit`.
3. Copy `server/.env.example` to `server/.env` and replace `SESSION_SECRET` with at least 32 random characters. The included database password is for local development only. The default SMTP settings deliver test messages to Mailpit.
4. Run `pnpm --filter @karmas-world/api db:deploy` to apply the checked-in migration.
5. Run `pnpm api:dev` to start the API at `http://localhost:4000`.

Open the local Mailpit inbox at `http://localhost:8025` to view verification and password reset messages. If no SMTP service is available in development, the API prints a local-only email preview with the link in its terminal output. Those links are account credentials; keep the output private and never enable this preview in production. For a native PostgreSQL setup, set `DATABASE_URL` as above and configure `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, and `SMTP_FROM` for a local test mail service or trusted provider.

The account endpoints are `GET /api/auth/csrf`, `POST /api/auth/register`, `POST /api/auth/verification/resend`, `POST /api/auth/verification/confirm`, `POST /api/auth/login`, `POST /api/auth/login/mfa`, `POST /api/auth/mfa/setup`, `POST /api/auth/mfa/enable`, `POST /api/auth/mfa/disable`, `POST /api/auth/logout`, `GET /api/auth/me`, `PATCH /api/auth/profile`, `PATCH /api/auth/password`, `POST /api/auth/password/reset/request`, `POST /api/auth/password/reset/complete`, `DELETE /api/auth/account`, `GET /api/auth/security/activity`, and `GET /api/auth/export`. New accounts cannot sign in before email verification. Verification links expire after 24 hours; reset links expire after one hour. Both are single-use random tokens, stored as SHA-256 hashes, and the request endpoints use generic responses to avoid revealing whether an email is registered. Recovery endpoints are rate limited. Completing a reset updates the Argon2id password hash and removes all sessions. Profile and in-session password changes require an authenticated session and CSRF token. In-session password changes also require the current password, allow five attempts per hour, require a new password between 15 and 128 characters, rotate the current session and CSRF token, and remove other active sessions. Account deletion requires the current password and the exact confirmation `DELETE`, is limited to three attempts per hour, and removes the account's data and active sessions in a transaction. The final administrator cannot delete their account. Learning progress uses authenticated `GET /api/progress` and CSRF-protected `PUT /api/progress`.

Authenticator MFA is optional. `POST /api/auth/mfa/setup` requires the current password, creates a pending secret that expires after ten minutes, and returns the secret once for manual entry in an authenticator app. `POST /api/auth/mfa/enable` confirms a six-digit code and returns ten recovery codes once. Only encrypted authenticator secrets and hashes of recovery codes are stored. MFA-enabled password sign-in creates a five-minute, unauthenticated challenge; `POST /api/auth/login/mfa` completes it with an authenticator or unused recovery code. TOTP codes are checked in the current or immediately previous 30-second time step and cannot be accepted twice. MFA enrollment, challenge, and recovery responses are marked `no-store`; MFA routes are rate limited. Password changes, account deletion, and disabling MFA also require and consume a second factor. Enabling and disabling MFA revoke the account's other sessions and rotate the current session and CSRF token. In production, set `MFA_ENCRYPTION_KEY` to a stable, private 32-byte key encoded as 64 hex characters, and back it up securely. Development derives a key from `SESSION_SECRET`; changing that secret requires re-enrolling MFA for existing local accounts.

Session controls use `GET /api/auth/sessions` to list unexpired sessions, `DELETE /api/auth/sessions/:sessionId` to revoke one other device, and `DELETE /api/auth/sessions` to revoke every other session while preserving the current one. All responses are `no-store`; deletion requests require the current CSRF token. Session rows are read and deleted from the PostgreSQL-backed `user_sessions` table, constrained to the signed-in account. Newly authenticated sessions record a timestamp and a truncated browser user-agent label; they do not record client IP addresses. Older sessions without that metadata are displayed without a device label or sign-in time.

`POST /api/auth/mfa/recovery-codes/rotate` requires the current password and a valid authenticator or unused recovery code. The request consumes the submitted factor, invalidates all previous recovery codes, stores hashes of ten new codes, revokes other active sessions, rotates the current session and CSRF token, and returns the new codes once in a `no-store` response.

Email changes use `POST /api/auth/email/change/request` and `POST /api/auth/email/change/confirm`. The request requires a signed-in session, current password, and MFA factor when enabled; it is limited to three requests per hour. The current email remains active until the learner explicitly submits the one-time confirmation link sent to the proposed address. Only a token hash and target address are stored, and the link expires after one hour. Confirmation rechecks uniqueness transactionally, marks the new address verified, removes remaining account tokens and sessions, clears the current session, and sends a notice to the previous address. A confirmation failure never changes the existing email.

The community API provides public `GET /api/community/posts` for approved posts; signed-in learners can submit posts and report approved posts. Every post starts in `PENDING`; only an `ADMIN` account can access `GET /api/community/moderation` or use the CSRF-protected moderation `PATCH` routes to approve or hide posts and resolve reports. Submission and report endpoints are rate limited, report duplicates are rejected, and public responses never include reporter identity. The frontend displays account display names on approved posts, so learners are told before submitting.

The leaderboard uses public `GET /api/leaderboard` and signed-in, CSRF-protected `PATCH /api/leaderboard/participation`. Participation defaults to off. Opted-in rows disclose only the account display name and server-counted completed lesson total; signed-in users can remove themselves from the board at any time. Progress uniqueness constraints prevent repeated completion requests from inflating the score.

The security brief is a manually curated frontend module. It shows its editorial check date, links to the original publishers, and is not a real-time incident alert service. Update the brief only after checking the linked primary sources and their publication dates.

`GET /api/admin/overview` is restricted to accounts whose server-side role is `ADMIN`. It returns aggregate counts for learner accounts, completed lessons, pending posts, open reports, and opted-in leaderboard participants. It never returns learner emails or individual progress records. Account roles are not assignable through public registration.

The security brief is managed with `GET /api/admin/news`, CSRF-protected `POST /api/admin/news` (always creates a draft), and CSRF-protected `PATCH /api/admin/news/:id` (edits content and visibility). Only HTTPS links hosted on NIST, CERT-In, or CISA domains are accepted, with the publisher label required to match the hostname. Public `GET /api/news` returns published entries only. The migration seeds the currently curated stories and stores editorial verification timestamps; check the original source before publishing or updating an entry.

`GET /api/auth/security/activity` requires a signed-in session and returns only that account’s latest 50 successful sign-ins and security changes. Entries can include a sanitized, 240-character browser user-agent label, but never an IP address. Security activity is private to the account and is removed when the account is deleted. `GET /api/auth/export` requires a signed-in session and returns that learner’s account profile, completion records, community posts and reports, security activity, and leaderboard preference. The response is marked `no-store` and does not include password hashes or session data. The frontend combines it with that learner’s browser-local progress and private reflections to create a JSON file on their device.

`DELETE /api/auth/account` also clears the account-scoped progress and private reflections from that browser after the server confirms deletion. Guest progress remains available on the device. Account-authored posts and reports are deleted; moderator references on other content are cleared, while the content itself remains.

New accounts default to the `LEARNER` role. Promote a trusted moderator only through controlled database administration; never add a role field to public registration. In production, configure `SMTP_HOST` to a remote mail service, set `SMTP_FROM`, and add provider credentials as needed; SMTP transport requires TLS and production startup rejects localhost mail settings. Before public deployment, establish moderator coverage, an escalation process, monitored mail delivery, TLS, production secrets, database backups, and operational monitoring.
